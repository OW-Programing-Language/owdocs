Overview

OW is an open-source programming language with indentation-based, YAML-inspired syntax. The Java-hosted distribution includes an interpreter, LLVM IR backend for an experimental native subset, CLI and bundled OwIDE. The interpreter runs object-oriented applications, modules and functors, web APIs, interactive UIs, tests and more.

What changed: OW gained classes, typed functions, imports, arrays and maps, floats, contracts, module calculus, OWUnit, exceptions, external dependencies, persistence and rapidly expanding native collections support.

OW is real code, not a YAML configuration parser. Start with ow run for the broadest feature support.

Installation

Download OW from the installation guide or GitHub Releases. Windows installer and portable runtime-bundled builds do not require separately installing Java. JVM distributions require Java 17+.

ow version
ow help
ow ide
ow run examples/oop_demo.ow

To build the language from source, use JDK 17+ and Maven:

git clone https://github.com/OW-Programing-Language/ow-lang.git
cd ow-lang
mvn clean package
java -jar target/OwIDE.jar help
Do not download the old downloads/OwIDE.jar link from previous documentation; release assets are published on GitHub. ow build also requires Clang/LLVM or Zig on the host.

Your first program

Save this as hello.ow. The top-level main: block runs the program and fn declares a reusable function:

fn greet(name: string):
  returns: string
  return: "Hello, " + name + "!"

main:
  set who: "OW"
  print: greet(who)
ow run hello.ow
# Hello, OW!

Use a consistent two-space indentation for all nested blocks. # begins a comment.

Syntax and indentation

OW combines keyword: value statements and indentation-defined blocks. No semicolons or braced statement blocks are needed.

# comment
main:
  set value: 2
  if: value > 1
    print: "greater"
  else:
    print: "smaller"

Top-level constructs include fn, class, enum, interface, model, module_type, module, functor, import and main:. Declarations and expressions are validated by the OW parser, not YAML tools.

Types, values and arithmetic

The interpreter supports integers, IEEE-754 floats, strings, booleans, arrays, records/maps, enums, class instances and module values. set declares or reassigns a variable, optionally with a type.

main:
  set count int: 10
  set label string: "score"
  set enabled bool: true
  print: label + ": " + str(count)
  print: 7 / 2       # 3 (integer)
  print: 7.0 / 2     # 3.5 (float)

Operators include + - * / == != < <= > >=. Integer-only division remains integer; arithmetic with a float promotes to floating-point. Convert with int, floor, ceil and round.

Control flow

OW supports if:/else:, else if, while:, and switch: with case/default:. A case can match several values.

main:
  set x: 2
  switch: x
    case 1:
      print: "one"
    case 2, 3:
      print: "two or three"
    default:
      print: "other"
  set i: 0
  while: i < 3
    print: i
    set i: i + 1

For native code, control-flow syntax is supported only when its expressions use natively supported types and operations.

Functions and typed signatures

The preferred YAML-style signature uses name: type parameters and a returns: type declaration at the start of the function body. The return: statement returns the actual value; call: discards a call result.

fn add(a: int, b: int):
  returns: int
  return: a + b

main:
  print: add(20, 22)

Legacy fn add(a int, b int) -> int: and untyped fn add(a, b): still work. Never combine an arrow return type and a body returns: declaration in the same function. Native reference-counted values need explicit types at function boundaries.

Arrays

main:
  set scores: [4, 8, 12]
  set scores[1]: 9
  set zeros: array(3, 0)
  print: scores[1]

Dictionaries and records

String-keyed maps preserve insertion order. Identifier keys also support dot access; direct missing-key indexing raises an error.

main:
  set profile: { name: "Ada", level: 3 }
  set profile["level"]: 4
  print: profile.name
  print: map_get(profile, "missing", "default")
  print: map_keys(profile)[0]

Map builtins: map_get (lazy fallback), map_has, map_set, map_delete, map_keys, map_values, map_size. Native map value types are more restricted than interpreter values.

Object-oriented programming

Classes support fields, the new constructor, instance methods and this. OW also has private/public members, inheritance, overrides, dynamic dispatch, enums and to_string().

class Person:
  field name
  fn new(value):
    set this.name: value
  fn hello():
    return: "Hi " + this.name

class Friend(Person):
  fn hello():
    return: "Hey " + this.name

main:
  set friend: new Friend("Ada")
  print: friend.hello()

Full OOP execution is interpreter-backed; general classes and object graphs are not yet LLVM-native.

Interfaces and contracts

interface declares an object's public method contract. OW checks implementations before main:: missing methods, private replacements, wrong arities, incompatible typed signatures and inheritance cycles are rejected.

interface Storage:
  fn put(key: string, value: int):
    returns: bool

class MemoryStorage(Storage):
  fn put(key: string, value: int):
    returns: bool
    return: true

Type annotations are optional but validated where present. This contract system is not a complete whole-program inference engine.

Module types, functors and abstract types

OW implements a tested subset of OCaml-inspired module calculus: module_type, module, functor, functor_gen, structural signature matching, opaque/manifest types, with_type sharing, aliases, nested modules, include, higher-order functors and first-class packages (pack/unpack).

module_type COUNTER:
  fn get() -> int

module Answer: COUNTER
  fn get() -> int:
    return: 42

main:
  print: Answer.get()

Public exports are sealed to declared signatures. Applicative functors preserve stable abstract-type identities; generative functors create fresh identities. ow check validates known module contracts without running main:.

Advanced module calculus

OW's module calculus is more than dependency injection: it checks named module signatures, abstract type identities, functor contracts and exposed public methods before running main:. The interpreter supports more module expressions than the experimental LLVM backend.

Signatures and implementation sharing

module_type LIFECYCLE:
  fn name() -> string
  fn start() -> int

module_type INVENTORY:
  include LIFECYCLE
  type sku
  fn issue(value int) -> sku

Signatures can include other signatures. Implementations can also include a statically known module, delegating its public exports and preserving inherited abstract-type identity. An api/ signature can be imported by infrastructure without exposing private implementation files.

Applicative versus generative functors

functor is applicative by default: the same functor applied to the same stable module path preserves abstract result type identity. functor_gen generates fresh identities. with_type can explicitly share an abstract type with a functor input, and manifest declarations type token: int expose representation as part of the contract.

Aliases, nesting and first-class modules

module Shop.Inventory = Warehouse
set sealed: pack(Warehouse, "READ")
set view READ: unpack(sealed, "READ")
print: view.get()

Transparent aliases preserve identity; nested named modules and their signatures have explicit public/private visibility. functor_type and return_functor: enable checked higher-order functors. pack/unpack seal a first-class module value. ow check performs a static preflight, but dynamic module packages and higher-order values are not general native LLVM values.

Not complete OCaml parity: general inference, mutually recursive modules, arbitrary dynamic first-class module lowering and all abstract representations remain out of scope. Check a specific example with ow check, then separately test ow llvm.

Projects, imports and boundaries

import "relative/file.ow" loads other OW files relative to the importing file. The entry file can hold main:, while components live in separate files. Missing imports and cycles are detected.

# src/main.ow
import "api/Math.ow"

main:
  print: add(5, 6)

Layouts using api/ and infra/ get enforced import boundaries. An API cannot import infrastructure, and one module cannot directly import another module's private infrastructure. The composition root may wire implementations together.

shop/
  main.ow
  inventory/api/InventoryApi.ow
  inventory/infra/Inventory.ow
  orders/api/OrdersApi.ow
  orders/infra/Orders.ow

This convention is relevant to the separate flOW framework.

Dependency management

A project-root dependencies.yml defines Git repositories and versioned OW source-library aliases. dependencies.lock.yml records resolved commits; installed sources are cached under .ow/deps/.

format: 1
repositories:
  - id: github
    url: https://github.com
dependencies:
  - name: math
    repository: github
    path: OW-Programing-Language/ow-math-questions
    version: c22d01cfee6be18d96d4c55b95b7e79892bca9f6
ow deps init
ow deps install
ow deps list
ow deps update
# import "@math/src/MathQuestions.ow"

Commit the manifest and lockfile; gitignore .ow/deps/. run, check, llvm, build and package resolve the nearest manifest. This is for direct OW source dependencies—not Maven packages, semver ranges or transitive dependency solving.

OWUnit and test runner

The interpreter discovers @Test, @BeforeEach and @AfterEach on zero-argument test functions and class methods. No main: is required. Class-based tests instantiate a new object for each test.

class CalculatorTest:
  field value
  @BeforeEach
  fn setup():
    set this.value: 2
  @Test
  fn addsNumbers():
    call: assert(this.value + 3 == 5, "wrong result")
  @AfterEach
  fn cleanup():
    set this.value: 0
ow test examples/owunit/CalculatorTest.ow
ow test tests/
ow test tests/CalculatorTest.ow --filter CalculatorTest.addsNumbers

Directory discovery matches *Test.ow and *_test.ow. A failure exits nonzero. The separate OWUnit repository offers additional assertions. Native LLVM does not run annotated tests.

OWUnit assertion library and test recipes

The ow test runner is a language feature; OWUnit is a separate OW source library that supplies assertion methods. OWUnit is not JUnit and it does not require a JUnit Java runtime.

Add OWUnit to a project

# dependencies.yml (merge into your existing manifest)
format: 1
repositories:
  - id: github
    url: https://github.com
dependencies:
  - name: owunit
    repository: github
    path: OW-Programing-Language/OWUnit
    version: main

For reproducible builds, replace version: main with an immutable commit or release tag. Run ow deps install and commit dependencies.lock.yml.

import "@owunit/src/OWAssert.ow"

class CalculatorTest:
  field checker
  @BeforeEach
  fn setup():
    set this.checker: new OWAssert()
  @Test
  fn additionWorks():
    call: this.checker.assertEquals(5, 2 + 3)
  @AfterEach
  fn teardown():
    print: "done"

Assertion methods

assertEquals, assertNotEquals, assertTrue, assertFalse, assertGreaterThan, assertLessThan, assertInRange, assertArrayLength, assertEmpty, assertNotEmpty, assertContains, assertNotContains, assertNull, assertNotNull and fail.

ow test tests/
ow test tests/CalculatorTest.ow --filter CalculatorTest.additionWorks

Directory discovery matches *Test.ow and *_test.ow. Annotated methods must have zero arguments. Class test instances require a zero-argument constructor. A failing assertion is catchable inside OW, and a failed test exits nonzero for CI. Native LLVM does not run annotated tests.

Exceptions and assertions

throw: raises an OW runtime exception. try: requires catch name: and/or finally:. The catch variable holds the error message; finally runs even on returns and errors. Failed assert(...) calls are catchable in the interpreter.

main:
  try:
    throw: "bad input"
  catch message:
    print: "Caught " + message
  finally:
    print: "cleanup"

Native compilation does not yet lower try/catch/finally; native array bounds and missing-map-key failures abort rather than throwing catchable OW errors.

String functions: behavior and examples

The interpreter provides text helpers for normalization, splitting and parsing. String indexes are zero-based. The functions below are interpreter-facing APIs; they should not be assumed to be available in LLVM compilation.

FunctionBehavior
upper(s), lower(s), trim(s)Case conversion and trimming edge whitespace.
substr(s, start, len)Substring; clamps out-of-range bounds.
index_of(s, sub), contains(s, sub)First index (or -1), and a 0/1 inclusion result.
replace(s, a, b)Replace every literal occurrence.
split(s, sep)Array of pieces; preserves empty fields. Empty separator splits into characters.
char_at(s, i)One-character string; empty string when out of range.
main:
  set name: upper(trim("  ow language  "))
  print: name                     # OW LANGUAGE
  set parts: split("a,,c", ",")
  print: len(parts)               # 3
  print: parts[1]                 # empty string
  print: index_of("language", "age")
  print: replace("a-b-a", "a", "x")
  print: char_at("OW", 99)        # empty string

See strings.md for edge cases. String lengths and Unicode behavior can differ between operations; the documented native len(string) uses Java-compatible UTF-16 length semantics.

Mathematics, floats and timing

OW's interpreter supports integers and floating-point numbers. 7 / 2 uses integer division, while 7.0 / 2 yields a floating-point value. LLVM's current native numeric subset is primarily integer-oriented: do not infer float support from interpreter examples.

APIPurpose
abs(n), min(a,b), max(a,b)Magnitude and bounds.
pow(base,exp), sqrt(n)Integer power and floor square root (integer inputs).
clamp(n,lo,hi), mod(a,b)Constrain a number and compute a remainder.
floor(x), ceil(x), round(x)Convert/round floating-point values.
sleep(ms), now_ms()Blocking delay and elapsed monotonic milliseconds since program start.
time_ms()Legacy wall-clock-based modulo counter; avoid for durations.
main:
  print: 7 / 2            # 3
  print: 7.0 / 2          # 3.5
  print: pow(3, 4)        # 81
  print: sqrt(26)        # 5
  print: clamp(99, 0, 10)
  set begin: now_ms()
  call: sleep(150)
  print: now_ms() - begin

Reject invalid arguments such as negative exponents for integer pow, negative integer sqrt inputs, or a clamp lower bound above its upper bound. now_ms() is for elapsed time, not a Unix timestamp; its documented counter is limited by an integer representation.

Save/load and JSON

save(path, value) writes JSON (creating parent folders). load(path) restores JSON or returns 0 when missing; exists(path) distinguishes missing files. json and json_parse work in memory.

main:
  set path: "save/player.json"
  if: exists(path)
    set player: load(path)
    print: player.name
  else:
    call: save(path, { name: "Ada", level: 1 })

Paths are relative to the working directory in normal runs and to packaged resource locations according to packaging rules.

Built-in model tables

A model declaration creates an auto-persisted table in ow-data.json, without an external SQL server. Customize its path with OW_DB_PATH or ow.db.path.

model Task:
  title string
  done bool

main:
  save Task: {title: "Write docs", done: false}
  set open: find Task where done == false
  print: len(open)
  delete Task where done == true

find Model reads all records; find Model where condition filters; save Model: inserts with automatic IDs; delete Model removes rows.

HTTP server and routes

The interpreter can serve HTTP routes without an external server framework. Combine route, respond: and serve: for JSON or text APIs.

main:
  route "GET /health":
    respond: {ok: true}
  route "GET /hello/:name":
    respond: {greeting: param("name")}
  serve: 8080

Helpers include param, query, body, body_json and response(status, payload). The request also exposes a req record. Explore Night for a separate higher-level OW web framework.

Runtime extensions and Java SPI

OW has an optional runtime extension mechanism for functionality supplied by external Java JARs. It is an interpreter/runtime capability, not a promise of native LLVM support. A provider implements dev.oreo.RuntimeExtension and registers itself at META-INF/services/dev.oreo.RuntimeExtension.

The OW builtin extension("provider.operation", ...) dispatches to a supporting provider. Zero or multiple matching providers are treated as runtime errors rather than silently guessing. Providers can also observe or reject HTTP requests using beforeRequest and afterRequest hooks.

# From a shell with the OW runtime JAR and optional Night platform:
java -cp 'OwIDE.jar:night-platform.jar' dev.oreo.Main run app.ow

# app.ow
main:
  call: extension("night.security.enable")
  route "GET /":
    respond: "protected"
  serve: 8080
The example classpath syntax is for macOS/Linux; Windows uses a semicolon separator. The extension provider and its configuration must exist for the operation to work. Adding a Java JAR to the classpath does not make its APIs automatically callable as OW source syntax.

OW's embedded HTTP server currently uses a single worker and a documented 1 MiB request-body limit. For Internet-facing deployments use a reverse proxy and enforce TLS, timeouts and request limits. The extension SPI is not, by itself, an authentication framework.

Running OW web services safely

The built-in route / serve server is useful for prototypes and local APIs. Treat public deployment as a separate engineering task: a simple OW HTTP handler does not provide TLS, authentication, session handling or production limits automatically.

Route and response example

main:
  route "GET /health":
    respond: {ok: true}

  route "POST /echo":
    set data: body_json()
    respond: response(201, data)

  serve: 8080

Before exposing it to the Internet

  • Place a hardened reverse proxy in front for HTTPS, slow-client protection and request/connection limits.
  • Keep secrets in environment/configuration rather than source; authenticate and authorize protected routes before executing business logic.
  • Account for the current single-worker server and 1 MiB request-body limit; validate input and bound computational work.
  • Monitor request/error behavior and use realistic deployment tests. A green unit-test suite is not equivalent to a security audit.

For server applications that need JDBC, migrations, bearer/JWT security, metrics or an outbox, see the optional Night platform. Its 0.2 candidate is not production-certified.

Web and native-window UI

OW renders a shared widget tree in a browser (ui_run or ui_run_web) or desktop window (ui_run_native). Buttons and input fields dispatch to functions or instance methods.

fn view():
  return: ui_col([
    ui_heading("Counter"),
    ui_text("Count " + str(count)),
    ui_button("+1", "increment")
  ])
fn increment():
  set count: count + 1
main:
  set count int: 0
  call: ui_run("view", "OW Counter")

Widgets include ui_heading, ui_text, ui_button, ui_input, ui_image, ui_bar, ui_space, ui_card, ui_backdrop, ui_row, ui_col, ui_grid and ui_disc. Use ui_stop to stop the UI.

Set OW_UI_MODE to select a backend; OW_UI_NO_BROWSER=1 prevents browser auto-launch.

Images, input fields and UI callbacks

The interpreter's ui_image(path) and ui_input(value, handler) are supported by the browser UI and native desktop renderer. Images resolve relative to the process working directory. An input handler receives the submitted text as a string when the user presses Enter.

class App:
  field word
  fn new():
    set this.word: ""
  fn on_word(value):
    set this.word: value
  fn view():
    return: ui_col([
      ui_heading("Image and input"),
      ui_image("assets/logo.png"),
      ui_input(this.word, "app.on_word"),
      ui_text(this.word)
    ])

main:
  set app: new App()
  call: ui_run("app.view", "OW Demo")

Instance callbacks use a dotted global-object method name such as app.on_word. Convert a submitted number with int(value). Web input submissions cause a rerender; the browser renderer maintains focus while the user types. On native windows, ui_input is a desktop text field.

Bundled resources depend on your working directory and the packaging rules. Use assets/ for images and test paths in both ow run and the packaged application. Image format support can differ by renderer.

LLVM native compilation overview

ow llvm emits LLVM IR and ow build compiles supported constructs to a standalone executable without a JVM. The compiler itself still requires Java. This is an experimental, incomplete subset, not full OW interpreter parity.

ow llvm examples/native_dynamic_strings.ow target/strings.ll
clang target/strings.ll -o target/strings
./target/strings

Native support includes procedural integer operations, typed function boundaries, UTF-8 strings, reference-counted integer/string arrays, specialized string-key dictionaries, nested native maps, ordered map snapshots and statically resolvable integer-only module/functor calls.

General classes, object graphs, floats, OWUnit, try/catch, database models, HTTP and UI runtimes remain interpreter-only. Unsupported operations must not be assumed to compile natively.

Native strings, arrays and ARC

Native string values can be UTF-8 literals or dynamic string + string concatenations. Comparisons are content-based; len(string) counts UTF-16 code units like the Java interpreter. Embedded NULs are unsupported.

fn make(size: int):
  returns: string_array
  return: array(size, "Hello " + "OW")

main:
  set names: make(3)
  print: names[0]
  print: len(names)

array (i32 integer arrays) and string_array support indexed mutation, dynamic construction, typed arguments/returns and ARC ownership. String arrays release child strings when their last owner exits. [] is an empty integer array; use array(0, "") for an empty native string array.

Reference counters are currently single-threaded, the ABI is experimental and bounds errors abort in native programs.

Native maps, nested values and iteration

Native dictionaries specialize string-keyed values as int_map, string_map or mixed_map (tagged integer, string and nested-map values). A resizing UTF-8 hash table provides average O(1) lookup.

main:
  set cfg: {name: "OW", version: 6}
  set keys: map_keys(cfg)
  set values: map_values(cfg)
  print: keys[0]
  print: cfg["name"]

map_keys/map_values create owned, insertion-ordered snapshots. Updating a key preserves its position; deleting and reinserting moves it to the end. mixed_map value snapshots use mixed_array.

Nested maps are managed by ARC with cycle prevention. Native maps do not yet cover arbitrary classes, floats, null, arrays as map values or full JSON lowering. Invalid native lookups may abort.

Native ABI and collection compatibility details

Native LLVM output runs without a JVM, but it compiles a typed subset. Some representations have explicit ownership rules and are evolving between revisions. A program that passes ow check or ow run can still be unsupported by ow llvm.

RepresentationSupported experimental behaviorImportant limit
array (i32)Literal, allocation, indexed read/write, len, typed function boundaries and reference counting.No general nested or mixed arbitrary-object arrays.
string_arrayDynamic UTF-8 string elements, copy/alias behavior and owned references.No general objects as elements; native string rules differ from arbitrary JVM values.
int_map, string_mapString-key lookup/update/delete, resizing hash table and ordered enumeration.Value types are homogeneous and explicit at native function boundaries.
mixed_mapTagged integer/string/nested-map values, dynamic access and reference-counted children.No general object, float, array-as-map-value or native JSON support.
mixed_arrayOwned snapshots from map_values, indexed reads and typed boundaries.Not a general-purpose arbitrary heterogeneous array literal/runtime.

Map snapshots and insertion order

main:
  set settings: {language: "OW", major: 1}
  set names: map_keys(settings)
  set values: map_values(settings)
  print: names[0]
  print: values[1]

map_keys and map_values return snapshots. Updating a key retains its original position; deletion and reinsertion move the key to the end. Nested maps have cycle guards. The native map implementation uses a resizing UTF-8 hash table with expected O(1) lookup and O(n) worst case.

Native reference counts are non-atomic. No general garbage collector or exception unwinding exists for arbitrary object graphs. ABI/layout changes mean older generated binaries may need recompilation. AddressSanitizer/LeakSanitizer tests cover examples; that does not make every program production-ready.

Native module/functor subset

The LLVM backend can lower some statically resolved integer module and functor calls, including documented qualified, opaque and packed static cases. It is not a general OCaml-compatible module compiler.

ow check examples/module_calculus/native_llvm.ow
ow llvm examples/module_calculus/native_llvm.ow target/native-modules.ll

ow check passing does not guarantee that ow llvm can compile a file: dynamically computed first-class modules and arbitrary higher-order functors remain interpreter-first.

OWler IDE: projects, dependencies and test runs

OWler IDE is a separate source project built with Tauri 2, Rust, React and Monaco. Its editor integrates OW CLI actions, dependencies and test discovery. It is not the same as the Java-based OwIDE included in ow-lang.

Daily workflow

  1. Create or open an OW project; new projects include starter source, a dependencies.yml and an OWUnit test fixture.
  2. Use the editor actions for ow check, ow run, ow llvm or ow build. LLVM IR is written to build/owler/.
  3. Right-click the root dependencies.yml and choose Reload Dependencies to run the resolver update, refresh the lockfile and reload project files.
  4. Run a test with a green gutter icon next to @Test, or use the Tests tool window to run a complete file/folder and inspect failures.
  5. Use Reload Project after external edits by an AI CLI; unsaved editor changes should not be silently overwritten.

ow deps update
ow check src/main.ow
ow test tests/
ow test tests/CalculatorTest.ow --filter CalculatorTest.additionWorks

The OWler repository documents an expanded editor and installer pipeline, but does not currently claim a verified production-ready Windows installation. Consult its build checks and release checklist before distributing installers. OWUnit tests run in the interpreter, not the LLVM backend.

Troubleshooting

  • ow not found: add the release bin/ to PATH, or run the JAR.
  • Java class version error: use Java 17+ or the runtime-bundled installer.
  • Native compiler missing: install LLVM/Clang or Zig; ow run does not need them.
  • Native unsupported type: try the interpreter and check the precise native feature page.
  • Unresolved @alias: run ow deps install, inspect the manifest and lockfile.
  • Test not discovered: filename must end with Test.ow or _test.ow.
  • Import boundary failure: depend on public api/, not another module's infra/.
  • Speech model missing: download a Vosk model and provide its directory explicitly.

When filing a bug, share a minimal source example and identify which of ow run, ow check or ow llvm fails.

flOW modular application framework

flOW is a separate framework combining native OW signatures/functors with a Spring Modulith-inspired runtime for services, dependencies, events and module lifecycle. It does not add new syntax to the OW compiler.

Native module bridge

set orders ORDERS: MakeOrders(Warehouse)
set app: new App()
call: app.use_native_as(orders, "ORDERS")
call: app.use_native_as(Warehouse, "INVENTORY")
call: assert(app.boot() == 1)
set inventory INVENTORY: app.service("inventory")
call: app.emit("order.placed", 5)
call: app.stop()

use_native and use_native_as register genuine typed module values with a runtime adapter, retaining checked exports on retrieval from the service registry. use also supports older class-based modules. Native event payloads currently use integer values and string event names.

Lifecycle rules

  • boot() starts providers in dependency order; stop() reverses startup order.
  • disable(name) prevents stopping a provider while active dependents require it; enable(name) reactivates only when dependencies are running.
  • reload(name) applies to a running module. emit dispatches only to enabled/running modules.
  • A negative start result aborts boot and rolls back successful starts.
Current runtime limits are 64 modules, 128 typed requirements and 64 service entries per registry; failed boot requires a fresh App instance. The bridge runs in the interpreter: LLVM does not generally lower lifecycle adapter values.

Night web framework and starter modules

Night builds modular OW web applications using the OW runtime, native OW module contracts and an optional Java ServiceLoader platform. Its inspiration is Spring Boot and Spring Modulith; it is not Spring Boot, and Java/Spring libraries are not automatically interoperable from OW.
