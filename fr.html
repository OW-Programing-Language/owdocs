Présentation

OW est un langage de programmation open source à indentation, avec une syntaxe inspirée du YAML. Sa distribution Java comprend un interpréteur, un générateur LLVM pour une partie expérimentale du langage, une CLI et l'IDE intégré OwIDE. L'interpréteur exécute des programmes orientés objet, des modules, des API HTTP, des interfaces interactives et des tests.

Les grandes nouveautés : fonctions typées, classes, imports, tableaux, dictionnaires, décimaux, interfaces, modules et foncteurs, OWUnit, exceptions, dépendances externes, persistance et nombreuses collections compilables en natif.

OW est du code avec une apparence YAML, pas un lecteur de fichiers de configuration YAML. Utilisez ow run pour profiter du plus grand nombre de fonctionnalités.

Installation

Téléchargez OW sur GitHub Releases. Les versions Windows avec installateur ou archive portable peuvent inclure leur propre runtime Java. Les distributions JVM nécessitent Java 17 ou supérieur.

ow version
ow help
ow ide
ow run examples/oop_demo.ow

Pour compiler le projet à partir des sources, installez JDK 17+ et Maven :

git clone https://github.com/OW-Programing-Language/ow-lang.git
cd ow-lang
mvn clean package
java -jar target/OwIDE.jar help
L'ancien lien downloads/OwIDE.jar de la documentation ne garantissait pas un fichier disponible : utilisez les assets GitHub Releases. La compilation native avec ow build demande également Clang/LLVM ou Zig.

Premier programme

Enregistrez ce code dans hello.ow. Le bloc main: est le point d'entrée, et fn déclare une fonction réutilisable :

fn greet(name: string):
  returns: string
  return: "Hello, " + name + "!"

main:
  set who: "OW"
  print: greet(who)
ow run hello.ow
# Hello, OW!

Utilisez une indentation cohérente de deux espaces pour les blocs imbriqués. # débute un commentaire.

Syntaxe et indentation

OW combine les instructions mot-clé: valeur avec des blocs structurés par indentation. Pas de point-virgule ni d'accolades autour des blocs d'instructions.

# commentaire
main:
  set value: 2
  if: value > 1
    print: "greater"
  else:
    print: "smaller"

On peut déclarer au niveau supérieur fn, class, enum, interface, model, module_type, module, functor, import et main:. C'est le parseur OW, et non un parseur YAML, qui valide ces constructions.

Types, variables et calculs

L'interpréteur gère les entiers, flottants IEEE-754, chaînes, booléens, tableaux, dictionnaires/enregistrements, énumérations, objets et valeurs de modules. set déclare ou réaffecte une variable, avec un type optionnel.

main:
  set count int: 10
  set label string: "score"
  set enabled bool: true
  print: label + ": " + str(count)
  print: 7 / 2       # 3 (entier)
  print: 7.0 / 2     # 3.5 (flottant)

Opérateurs : + - * / == != < <= > >=. La division de deux entiers reste entière ; un opérande flottant active le calcul décimal. Pour convertir, utilisez int, floor, ceil et round.

Conditions, boucles et switch

OW propose if:/else:, else if, while: et switch: avec case/default:. Un case peut contenir plusieurs valeurs.

main:
  set x: 2
  switch: x
    case 1:
      print: "one"
    case 2, 3:
      print: "two or three"
    default:
      print: "other"
  set i: 0
  while: i < 3
    print: i
    set i: i + 1

En natif, ces structures ne fonctionnent que si leurs expressions sont compatibles avec le sous-ensemble LLVM pris en charge.

Fonctions et signatures typées

La syntaxe YAML recommandée utilise nom: type pour les paramètres et returns: type en première ligne du corps. returns: décrit la signature ; return: renvoie une valeur. call: ignore le résultat d'un appel.

fn add(a: int, b: int):
  returns: int
  return: a + b

main:
  print: add(20, 22)

Les anciennes formes fn add(a int, b int) -> int: et fn add(a, b): restent valides. N'utilisez pas -> type et returns: type ensemble sur la même fonction. La compilation native demande des types explicites pour les références aux tableaux, chaînes et dictionnaires.

Dictionnaires et enregistrements

Les maps utilisent des clés chaînes et préservent l'ordre d'insertion. Les clés simples sont accessibles avec .champ ; une clé inexistante accédée directement déclenche une erreur.

main:
  set profile: { name: "Ada", level: 3 }
  set profile["level"]: 4
  print: profile.name
  print: map_get(profile, "missing", "default")
  print: map_keys(profile)[0]

Fonctions : map_get (valeur par défaut évaluée à la demande), map_has, map_set, map_delete, map_keys, map_values, map_size. Les types de valeurs natifs sont plus limités que ceux de l'interpréteur.

Programmation orientée objet

Les classes disposent de champs, d'un constructeur new, de méthodes et de this. OW prend aussi en charge les membres private/public, l'héritage, la redéfinition, le dispatch dynamique, les énumérations et to_string().

class Person:
  field name
  fn new(value):
    set this.name: value
  fn hello():
    return: "Hi " + this.name

class Friend(Person):
  fn hello():
    return: "Hey " + this.name

main:
  set friend: new Friend("Ada")
  print: friend.hello()

La POO complète fonctionne dans l'interpréteur ; les classes et graphes d'objets génériques ne sont pas encore compilés directement par LLVM.

Interfaces et contrats

Une interface définit les méthodes publiques attendues. OW vérifie les implémentations avant main: : méthodes absentes, visibilité incorrecte, nombre d'arguments, signatures typées incompatibles et cycles d'héritage.

interface Storage:
  fn put(key: string, value: int):
    returns: bool

class MemoryStorage(Storage):
  fn put(key: string, value: int):
    returns: bool
    return: true

Les types sont optionnels mais vérifiés lorsqu'ils sont déclarés. Ce système de contrats ne remplace pas une inférence statique complète de tout le programme.

Modules, foncteurs et types abstraits

OW implémente une partie testée du calcul de modules inspiré d'OCaml : module_type, module, functor, functor_gen, compatibilité structurelle des signatures, types opaques ou manifestes, partage via with_type, alias, modules imbriqués, include, foncteurs d'ordre supérieur et modules de première classe (pack/unpack).

module_type COUNTER:
  fn get() -> int

module Answer: COUNTER
  fn get() -> int:
    return: 42

main:
  print: Answer.get()

Les exports publics sont limités à la signature déclarée. Les foncteurs applicatifs conservent l'identité des types abstraits à partir de chemins stables ; les foncteurs génératifs créent de nouvelles identités. ow check vérifie les contrats avant exécution.

Projets, imports et isolation

import "chemin/relatif.ow" importe un autre fichier OW relativement au fichier courant. Le point d'entrée peut contenir main: pendant que les classes et utilitaires vivent dans d'autres fichiers. Le chargeur détecte les cycles et imports manquants.

# src/main.ow
import "api/Math.ow"

main:
  print: add(5, 6)

Les dossiers api/ et infra/ imposent des frontières : une API ne doit pas importer une infrastructure, et un module ne peut pas importer directement l'implémentation privée d'un autre. La racine de composition peut assembler les implémentations.

shop/
  main.ow
  inventory/api/InventoryApi.ow
  inventory/infra/Inventory.ow
  orders/api/OrdersApi.ow
  orders/infra/Orders.ow

Cette convention aide notamment les projets utilisant le framework externe flOW.

Gestion des dépendances

Un fichier dependencies.yml à la racine déclare des dépôts Git et leurs bibliothèques de sources OW, avec des alias. dependencies.lock.yml verrouille les commits exacts ; le cache local est dans .ow/deps/.

format: 1
repositories:
  - id: github
    url: https://github.com
dependencies:
  - name: math
    repository: github
    path: OW-Programing-Language/ow-math-questions
    version: c22d01cfee6be18d96d4c55b95b7e79892bca9f6
ow deps init
ow deps install
ow deps list
ow deps update
# import "@math/src/MathQuestions.ow"

Versionnez le manifeste et le lockfile, mais ignorez .ow/deps/. Les commandes run, check, llvm, build et package résolvent le manifeste du projet. Il ne s'agit pas d'un gestionnaire Maven, et les dépendances transitives ou contraintes semver ne sont pas encore prises en charge.

OWUnit et tests

L'interpréteur reconnaît @Test, @BeforeEach et @AfterEach sur les fonctions de test sans argument et les méthodes de classes sans argument. Aucun bloc main: n'est requis ; un nouvel objet est créé pour chaque test de classe.

class CalculatorTest:
  field value
  @BeforeEach
  fn setup():
    set this.value: 2
  @Test
  fn addsNumbers():
    call: assert(this.value + 3 == 5, "wrong result")
  @AfterEach
  fn cleanup():
    set this.value: 0
ow test examples/owunit/CalculatorTest.ow
ow test tests/
ow test tests/CalculatorTest.ow --filter CalculatorTest.addsNumbers

La découverte récursive cherche les fichiers terminés par Test.ow ou _test.ow. Un échec entraîne un code de sortie non nul. Le dépôt séparé OWUnit fournit d'autres assertions. Les annotations de test restent réservées à l'interpréteur.

Exceptions et assertions

throw: lève une exception OW. Un bloc try: nécessite catch nom: et/ou finally:. La variable du catch reçoit le message d'erreur ; finally s'exécute également lors d'un retour ou d'une exception. Les erreurs assert(...) sont interceptables dans l'interpréteur.

main:
  try:
    throw: "bad input"
  catch message:
    print: "Caught " + message
  finally:
    print: "cleanup"

Le backend LLVM ne prend pas encore en charge try/catch/finally. Les erreurs natives d'indexation ou de clé absente peuvent arrêter le processus.

Sauvegarde et JSON

save(path, value) écrit un fichier JSON en créant les dossiers parents. load(path) le relit ou renvoie 0 s'il manque ; exists(path) vérifie sa présence. json et json_parse convertissent les données en mémoire.

main:
  set path: "save/player.json"
  if: exists(path)
    set player: load(path)
    print: player.name
  else:
    call: save(path, {name: "Ada", level: 1})

Les chemins relatifs sont résolus depuis le répertoire de travail, ou depuis les ressources de l'application lors de l'empaquetage.

Tables de données intégrées

Une déclaration model crée une table sauvegardée automatiquement dans ow-data.json, sans serveur SQL. Vous pouvez changer l'emplacement avec OW_DB_PATH ou ow.db.path.

model Task:
  title string
  done bool

main:
  save Task: {title: "Write docs", done: false}
  set open: find Task where done == false
  print: len(open)
  delete Task where done == true

find Model lit les lignes, find Model where condition filtre, save Model: insère avec un identifiant automatique et delete Model supprime des enregistrements.

Serveur HTTP et routes

L'interpréteur peut exposer des routes HTTP sans serveur externe. Combinez route, respond: et serve: pour créer une API JSON ou texte.

main:
  route "GET /health":
    respond: {ok: true}
  route "GET /hello/:name":
    respond: {greeting: param("name")}
  serve: 8080

Fonctions utiles : param, query, body, body_json et response(status, payload). Les informations de requête existent aussi dans req. Consultez Night pour un framework web OW distinct et plus haut niveau.

Interfaces web et fenêtres natives

OW peut afficher le même arbre de composants dans un navigateur (ui_run ou ui_run_web) et dans une fenêtre de bureau (ui_run_native). Les boutons et champs de saisie appellent des fonctions OW.

fn view():
  return: ui_col([
    ui_heading("Counter"),
    ui_text("Count " + str(count)),
    ui_button("+1", "increment")
  ])
fn increment():
  set count: count + 1
main:
  set count int: 0
  call: ui_run("view", "OW Counter")

Composants : ui_heading, ui_text, ui_button, ui_input, ui_image, ui_bar, ui_space, ui_card, ui_backdrop, ui_row, ui_col, ui_grid et ui_disc. ui_stop arrête l'interface.

OW_UI_MODE sélectionne le moteur ; OW_UI_NO_BROWSER=1 évite l'ouverture automatique du navigateur.

Présentation de la compilation native LLVM

ow llvm génère du LLVM IR et ow build produit un exécutable autonome pour les constructions compatibles, sans JVM nécessaire à l'exécution. Le compilateur continue de dépendre de Java. Le sous-ensemble natif reste expérimental et incomplet.

ow llvm examples/native_dynamic_strings.ow target/strings.ll
clang target/strings.ll -o target/strings
./target/strings

Le support actuel couvre notamment les opérations entières, les fonctions typées, les chaînes UTF-8, les tableaux d'entiers/chaînes avec comptage de références, des dictionnaires spécialisés, des dictionnaires imbriqués, l'itération ordonnée et certains appels statiques à des modules/foncteurs entiers.

Les classes générales, flottants, OWUnit, try/catch, modèles de données, serveurs HTTP et interfaces graphiques ne disposent pas encore d'un support natif complet.

Chaînes, tableaux natifs et gestion mémoire

Les chaînes natives utilisent UTF-8 et prennent en charge la concaténation string + string, les comparaisons de contenu et len(string) avec la sémantique Java UTF-16. Les chaînes contenant un octet NUL intégré ne sont pas prises en charge.

fn make(size: int):
  returns: string_array
  return: array(size, "Hello " + "OW")

main:
  set names: make(3)
  print: names[0]
  print: len(names)

Les types array (entiers i32) et string_array gèrent les indices, mutations, allocations dynamiques, paramètres/retours typés et le comptage de références ARC. Les tableaux de chaînes libèrent aussi les chaînes contenues lorsqu'ils n'ont plus de propriétaire. [] crée un tableau entier vide ; pour un tableau natif de chaînes vide, utilisez array(0, "").

Les compteurs ne sont pas atomiques, l'ABI reste instable et les erreurs d'indices peuvent arrêter l'exécutable natif.

Dictionnaires natifs et parcours ordonné

LLVM dispose de maps à clés chaînes : int_map, string_map et mixed_map (valeurs typées entiers, chaînes ou maps imbriquées). Une table de hachage UTF-8 redimensionnable offre une recherche moyenne en O(1).

main:
  set cfg: {name: "OW", version: 6}
  set keys: map_keys(cfg)
  set values: map_values(cfg)
  print: keys[0]
  print: cfg["name"]

map_keys et map_values renvoient des instantanés propriétaires dans l'ordre d'insertion. Modifier une clé ne change pas sa position ; la supprimer puis la recréer la déplace à la fin. Les valeurs d'une mixed_map sont regroupées dans un mixed_array.

Les maps imbriquées utilisent ARC avec prévention des cycles. Le natif n'accepte pas encore les objets arbitraires, flottants, valeurs nulles, tableaux en valeur de map ni toutes les opérations JSON.

Modules et foncteurs en natif

Le backend LLVM peut compiler certains appels statiquement résolus à des modules ou foncteurs entiers, notamment des variantes qualifiées, opaques ou empaquetées documentées. Il ne constitue pas un compilateur de modules OCaml complet.

ow check examples/module_calculus/native_llvm.ow
ow llvm examples/module_calculus/native_llvm.ow target/native-modules.ll

Un fichier validé par ow check n'est pas forcément compilable avec ow llvm. Les modules dynamiques de première classe et les foncteurs arbitraires restent principalement interprétés.

OwIDE et OWler-IDE

L'OwIDE fourni avec ow-lang est un éditeur Java de bureau comprenant navigation de projet, exécution/compilation et boutons de lancement des interfaces web ou natives. Lancez-le avec ow ide ou via le programme distribué dans Releases.

OWler-IDE est un projet distinct, basé sur Tauri/Rust/React. Ses fonctionnalités, installateurs et versions doivent être vérifiés dans son propre dépôt, sans les confondre avec l'OwIDE Java fourni par le langage.

Résolution des problèmes

  • ow introuvable : ajoutez le répertoire bin/ au PATH, ou exécutez le JAR.
  • Version Java incompatible : utilisez Java 17+ ou un installateur avec runtime inclus.
  • Compilateur natif absent : installez LLVM/Clang ou Zig ; ow run n'en a pas besoin.
  • Type non pris en charge par LLVM : testez avec l'interpréteur et consultez la documentation précise du type natif.
  • Import @alias introuvable : lancez ow deps install et vérifiez le manifeste/lockfile.
  • Test non découvert : nommez le fichier avec le suffixe Test.ow ou _test.ow.
  • Erreur de frontière d'import : utilisez api/ plutôt que l'infra/ privée d'un autre module.
  • Modèle vocal absent : téléchargez un modèle Vosk et fournissez son dossier.

Pour signaler un bug, joignez un petit programme reproduisant l'erreur et précisez si le problème apparaît avec ow run, ow check ou ow llvm.

fn add(a: int, b: int):
  returns: int
  return: a + b

main:
  set values: [1, 2, 3]
  set values[0]: 5
  set cfg: {mode: "dev", count: 2}
  if: map_has(cfg, "mode")
    print: cfg.mode
  print: add(values[0], cfg.count)
