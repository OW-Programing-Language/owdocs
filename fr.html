Documentation OW

Présentation

OW est un langage de programmation open source à indentation, avec une syntaxe inspirée du YAML. Sa distribution Java comprend un interpréteur, un générateur LLVM pour une partie expérimentale du langage, une CLI et l'IDE intégré OwIDE. L'interpréteur exécute des programmes orientés objet, des modules, des API HTTP, des interfaces interactives et des tests.

Les grandes nouveautés : fonctions typées, classes, imports, tableaux, dictionnaires, décimaux, interfaces, modules et foncteurs, OWUnit, exceptions, dépendances externes, persistance et nombreuses collections compilables en natif.

OW est du code avec une apparence YAML, pas un lecteur de fichiers de configuration YAML. Utilisez ow run pour profiter du plus grand nombre de fonctionnalités.

Installation

Téléchargez OW sur GitHub Releases. Les versions Windows avec installateur ou archive portable peuvent inclure leur propre runtime Java. Les distributions JVM nécessitent Java 17 ou supérieur.

ow version
ow help
ow ide
ow run examples/oop_demo.ow

Pour compiler le projet à partir des sources, installez JDK 17+ et Maven :

git clone https://github.com/OW-Programing-Language/ow-lang.git
cd ow-lang
mvn clean package
java -jar target/OwIDE.jar help
L'ancien lien downloads/OwIDE.jar de la documentation ne garantissait pas un fichier disponible : utilisez les assets GitHub Releases. La compilation native avec ow build demande également Clang/LLVM ou Zig.

Premier programme

Enregistrez ce code dans hello.ow. Le bloc main: est le point d'entrée, et fn déclare une fonction réutilisable :

fn greet(name: string):
  returns: string
  return: "Hello, " + name + "!"

main:
  set who: "OW"
  print: greet(who)
ow run hello.ow
# Hello, OW!

Utilisez une indentation cohérente de deux espaces pour les blocs imbriqués. # débute un commentaire.

Syntaxe et indentation

OW combine les instructions mot-clé: valeur avec des blocs structurés par indentation. Pas de point-virgule ni d'accolades autour des blocs d'instructions.

# commentaire
main:
  set value: 2
  if: value > 1
    print: "greater"
  else:
    print: "smaller"

On peut déclarer au niveau supérieur fn, class, enum, interface, model, module_type, module, functor, import et main:. C'est le parseur OW, et non un parseur YAML, qui valide ces constructions.

Types, variables et calculs

L'interpréteur gère les entiers, flottants IEEE-754, chaînes, booléens, tableaux, dictionnaires/enregistrements, énumérations, objets et valeurs de modules. set déclare ou réaffecte une variable, avec un type optionnel.

main:
  set count int: 10
  set label string: "score"
  set enabled bool: true
  print: label + ": " + str(count)
  print: 7 / 2       # 3 (entier)
  print: 7.0 / 2     # 3.5 (flottant)

Opérateurs : + - * / == != < <= > >=. La division de deux entiers reste entière ; un opérande flottant active le calcul décimal. Pour convertir, utilisez int, floor, ceil et round.

Conditions, boucles et switch

OW propose if:/else:, else if, while: et switch: avec case/default:. Un case peut contenir plusieurs valeurs.

main:
  set x: 2
  switch: x
    case 1:
      print: "one"
    case 2, 3:
      print: "two or three"
    default:
      print: "other"
  set i: 0
  while: i < 3
    print: i
    set i: i + 1

En natif, ces structures ne fonctionnent que si leurs expressions sont compatibles avec le sous-ensemble LLVM pris en charge.

Fonctions et signatures typées

La syntaxe YAML recommandée utilise nom: type pour les paramètres et returns: type en première ligne du corps. returns: décrit la signature ; return: renvoie une valeur. call: ignore le résultat d'un appel.

fn add(a: int, b: int):
  returns: int
  return: a + b

main:
  print: add(20, 22)

Les anciennes formes fn add(a int, b int) -> int: et fn add(a, b): restent valides. N'utilisez pas -> type et returns: type ensemble sur la même fonction. La compilation native demande des types explicites pour les références aux tableaux, chaînes et dictionnaires.

Dictionnaires et enregistrements

Les maps utilisent des clés chaînes et préservent l'ordre d'insertion. Les clés simples sont accessibles avec .champ ; une clé inexistante accédée directement déclenche une erreur.

main:
  set profile: { name: "Ada", level: 3 }
  set profile["level"]: 4
  print: profile.name
  print: map_get(profile, "missing", "default")
  print: map_keys(profile)[0]

Fonctions : map_get (valeur par défaut évaluée à la demande), map_has, map_set, map_delete, map_keys, map_values, map_size. Les types de valeurs natifs sont plus limités que ceux de l'interpréteur.

Programmation orientée objet

Les classes disposent de champs, d'un constructeur new, de méthodes et de this. OW prend aussi en charge les membres private/public, l'héritage, la redéfinition, le dispatch dynamique, les énumérations et to_string().

class Person:
  field name
  fn new(value):
    set this.name: value
  fn hello():
    return: "Hi " + this.name

class Friend(Person):
  fn hello():
    return: "Hey " + this.name

main:
  set friend: new Friend("Ada")
  print: friend.hello()

La POO complète fonctionne dans l'interpréteur ; les classes et graphes d'objets génériques ne sont pas encore compilés directement par LLVM.

Interfaces et contrats

Une interface définit les méthodes publiques attendues. OW vérifie les implémentations avant main: : méthodes absentes, visibilité incorrecte, nombre d'arguments, signatures typées incompatibles et cycles d'héritage.

interface Storage:
  fn put(key: string, value: int):
    returns: bool

class MemoryStorage(Storage):
  fn put(key: string, value: int):
    returns: bool
    return: true

Les types sont optionnels mais vérifiés lorsqu'ils sont déclarés. Ce système de contrats ne remplace pas une inférence statique complète de tout le programme.

Modules, foncteurs et types abstraits

OW implémente une partie testée du calcul de modules inspiré d'OCaml : module_type, module, functor, functor_gen, compatibilité structurelle des signatures, types opaques ou manifestes, partage via with_type, alias, modules imbriqués, include, foncteurs d'ordre supérieur et modules de première classe (pack/unpack).

module_type COUNTER:
  fn get() -> int

module Answer: COUNTER
  fn get() -> int:
    return: 42

main:
  print: Answer.get()

Les exports publics sont limités à la signature déclarée. Les foncteurs applicatifs conservent l'identité des types abstraits à partir de chemins stables ; les foncteurs génératifs créent de nouvelles identités. ow check vérifie les contrats avant exécution.

Calcul avancé des modules

Le système de modules d'OW ne se limite pas à l'injection de dépendances : il vérifie les signatures nommées, les identités des types abstraits, les contrats des foncteurs et les exports publics avant main:. L'interpréteur prend en charge davantage d'expressions modulaires que le backend LLVM expérimental.

Signatures et partage des implémentations

module_type LIFECYCLE:
  fn name() -> string
  fn start() -> int

module_type INVENTORY:
  include LIFECYCLE
  type sku
  fn issue(value int) -> sku

Une signature peut include d'autres signatures. Une implémentation peut inclure un module connu statiquement : les exports publics sont délégués, en préservant l'identité des types abstraits hérités. Les modules infra/ peuvent importer les signatures publiques api/ sans exposer l'implémentation privée.

Foncteurs applicatifs et génératifs

functor est applicatif par défaut : même foncteur et même chemin stable de module impliquent une identité de type abstrait préservée. functor_gen crée de nouvelles identités. with_type partage explicitement un type avec l'argument et type token: int expose sa représentation dans le contrat.

Alias, imbrication et modules de première classe

module Shop.Inventory = Warehouse
set sealed: pack(Warehouse, "READ")
set view READ: unpack(sealed, "READ")
print: view.get()

Les alias transparents préservent l'identité. Les modules nommés imbriqués contrôlent les exports publics/privés. functor_type et return_functor: permettent des foncteurs d'ordre supérieur vérifiés. pack/unpack encapsulent un module de première classe. ow check fait une vérification préalable, mais les paquets dynamiques et les valeurs d'ordre supérieur ne constituent pas des valeurs LLVM natives générales.

OW n'offre pas encore toute la sémantique d'OCaml : inférence générale, modules mutuellement récursifs et conversion native arbitraire des modules dynamiques restent limités. Vérifiez avec ow check, puis testez séparément ow llvm.

Projets, imports et isolation

import "chemin/relatif.ow" importe un autre fichier OW relativement au fichier courant. Le point d'entrée peut contenir main: pendant que les classes et utilitaires vivent dans d'autres fichiers. Le chargeur détecte les cycles et imports manquants.

# src/main.ow
import "api/Math.ow"

main:
  print: add(5, 6)

Les dossiers api/ et infra/ imposent des frontières : une API ne doit pas importer une infrastructure, et un module ne peut pas importer directement l'implémentation privée d'un autre. La racine de composition peut assembler les implémentations.

shop/
  main.ow
  inventory/api/InventoryApi.ow
  inventory/infra/Inventory.ow
  orders/api/OrdersApi.ow
  orders/infra/Orders.ow

Cette convention aide notamment les projets utilisant le framework externe flOW.

Gestion des dépendances

Un fichier dependencies.yml à la racine déclare des dépôts Git et leurs bibliothèques de sources OW, avec des alias. dependencies.lock.yml verrouille les commits exacts ; le cache local est dans .ow/deps/.

format: 1
repositories:
  - id: github
    url: https://github.com
dependencies:
  - name: math
    repository: github
    path: OW-Programing-Language/ow-math-questions
    version: c22d01cfee6be18d96d4c55b95b7e79892bca9f6
ow deps init
ow deps install
ow deps list
ow deps update
# import "@math/src/MathQuestions.ow"

Versionnez le manifeste et le lockfile, mais ignorez .ow/deps/. Les commandes run, check, llvm, build et package résolvent le manifeste du projet. Il ne s'agit pas d'un gestionnaire Maven, et les dépendances transitives ou contraintes semver ne sont pas encore prises en charge.

OWUnit et tests

L'interpréteur reconnaît @Test, @BeforeEach et @AfterEach sur les fonctions de test sans argument et les méthodes de classes sans argument. Aucun bloc main: n'est requis ; un nouvel objet est créé pour chaque test de classe.

class CalculatorTest:
  field value
  @BeforeEach
  fn setup():
    set this.value: 2
  @Test
  fn addsNumbers():
    call: assert(this.value + 3 == 5, "wrong result")
  @AfterEach
  fn cleanup():
    set this.value: 0
ow test examples/owunit/CalculatorTest.ow
ow test tests/
ow test tests/CalculatorTest.ow --filter CalculatorTest.addsNumbers

La découverte récursive cherche les fichiers terminés par Test.ow ou _test.ow. Un échec entraîne un code de sortie non nul. Le dépôt séparé OWUnit fournit d'autres assertions. Les annotations de test restent réservées à l'interpréteur.

Assertions OWUnit et recettes de tests

La commande ow test fait partie du langage ; OWUnit est une bibliothèque source OW séparée qui fournit des assertions plus expressives. Elle ne dépend pas du moteur JUnit Java.

Ajouter OWUnit au projet

# dependencies.yml (à intégrer au manifeste existant)
format: 1
repositories:
  - id: github
    url: https://github.com
dependencies:
  - name: owunit
    repository: github
    path: OW-Programing-Language/OWUnit
    version: main

Pour des builds reproductibles, remplacez version: main par un commit immuable ou une version publiée. Lancez ow deps install et commitez dependencies.lock.yml.

import "@owunit/src/OWAssert.ow"

class CalculatorTest:
  field checker
  @BeforeEach
  fn setup():
    set this.checker: new OWAssert()
  @Test
  fn additionWorks():
    call: this.checker.assertEquals(5, 2 + 3)
  @AfterEach
  fn teardown():
    print: "done"

Méthodes disponibles

assertEquals, assertNotEquals, assertTrue, assertFalse, assertGreaterThan, assertLessThan, assertInRange, assertArrayLength, assertEmpty, assertNotEmpty, assertContains, assertNotContains, assertNull, assertNotNull et fail.

ow test tests/
ow test tests/CalculatorTest.ow --filter CalculatorTest.additionWorks

La découverte dans un dossier reconnaît *Test.ow et *_test.ow. Les tests annotés ne prennent pas d'arguments ; les tests de classe nécessitent un constructeur sans argument. Une assertion échouée est rattrapable dans OW, et un test en échec retourne un code non nul pour la CI. Le backend LLVM ne lance pas ces tests.

Exceptions et assertions

throw: lève une exception OW. Un bloc try: nécessite catch nom: et/ou finally:. La variable du catch reçoit le message d'erreur ; finally s'exécute également lors d'un retour ou d'une exception. Les erreurs assert(...) sont interceptables dans l'interpréteur.

main:
  try:
    throw: "bad input"
  catch message:
    print: "Caught " + message
  finally:
    print: "cleanup"

Le backend LLVM ne prend pas encore en charge try/catch/finally. Les erreurs natives d'indexation ou de clé absente peuvent arrêter le processus.

Chaînes de caractères : fonctions et exemples

L'interpréteur fournit des outils pour normaliser, découper et analyser des chaînes. Les indices commencent à zéro. Les fonctions de cette page concernent l'interpréteur : leur présence ne garantit pas leur prise en charge par LLVM.

FonctionComportement
upper(s), lower(s), trim(s)Majuscules, minuscules et suppression des espaces autour du texte.
substr(s, start, len)Sous-chaîne ; les indices hors limites sont corrigés.
index_of(s, sub), contains(s, sub)Premier indice (ou -1) et résultat d'inclusion 0/1.
replace(s, a, b)Remplace toutes les occurrences littérales.
split(s, sep)Tableau de segments ; conserve les segments vides. Séparateur vide : caractère par caractère.
char_at(s, i)Caractère à l'indice demandé ; chaîne vide hors limites.
main:
  set name: upper(trim("  ow language  "))
  print: name                     # OW LANGUAGE
  set parts: split("a,,c", ",")
  print: len(parts)               # 3
  print: parts[1]                 # chaîne vide
  print: index_of("language", "age")
  print: replace("a-b-a", "a", "x")
  print: char_at("OW", 99)        # chaîne vide

Voir strings.md pour les cas limites. Le calcul de la longueur et les opérations Unicode peuvent varier ; le len(string) natif documenté adopte la longueur UTF-16 compatible Java.

Mathématiques, décimaux et temps

L'interpréteur OW prend en charge les entiers et les nombres à virgule flottante. 7 / 2 effectue une division entière, tandis que 7.0 / 2 donne un résultat décimal. Le backend LLVM gère principalement un sous-ensemble numérique entier : les exemples d'interpréteur ne prouvent pas la compatibilité native.

APIUtilité
abs(n), min(a,b), max(a,b)Valeur absolue et bornes.
pow(base,exp), sqrt(n)Puissance entière et racine carrée entière arrondie vers le bas.
clamp(n,lo,hi), mod(a,b)Limiter une valeur et calculer le reste.
floor(x), ceil(x), round(x)Arrondir ou convertir les flottants.
sleep(ms), now_ms()Attente bloquante et durée monotone en millisecondes depuis le démarrage.
time_ms()Ancien compteur d'horloge, soumis à un modulo ; déconseillé pour les durées.
main:
  print: 7 / 2            # 3
  print: 7.0 / 2          # 3.5
  print: pow(3, 4)        # 81
  print: sqrt(26)        # 5
  print: clamp(99, 0, 10)
  set begin: now_ms()
  call: sleep(150)
  print: now_ms() - begin

Les arguments invalides produisent des erreurs, par exemple exposant négatif pour pow entier, racine d'un entier négatif ou bornes inversées pour clamp. now_ms() mesure une durée, pas une date Unix ; sa portée est limitée par sa représentation entière.

Sauvegarde et JSON

save(path, value) écrit un fichier JSON en créant les dossiers parents. load(path) le relit ou renvoie 0 s'il manque ; exists(path) vérifie sa présence. json et json_parse convertissent les données en mémoire.

main:
  set path: "save/player.json"
  if: exists(path)
    set player: load(path)
    print: player.name
  else:
    call: save(path, {name: "Ada", level: 1})

Les chemins relatifs sont résolus depuis le répertoire de travail, ou depuis les ressources de l'application lors de l'empaquetage.

Tables de données intégrées

Une déclaration model crée une table sauvegardée automatiquement dans ow-data.json, sans serveur SQL. Vous pouvez changer l'emplacement avec OW_DB_PATH ou ow.db.path.

model Task:
  title string
  done bool

main:
  save Task: {title: "Write docs", done: false}
  set open: find Task where done == false
  print: len(open)
  delete Task where done == true

find Model lit les lignes, find Model where condition filtre, save Model: insère avec un identifiant automatique et delete Model supprime des enregistrements.

Serveur HTTP et routes

L'interpréteur peut exposer des routes HTTP sans serveur externe. Combinez route, respond: et serve: pour créer une API JSON ou texte.

main:
  route "GET /health":
    respond: {ok: true}
  route "GET /hello/:name":
    respond: {greeting: param("name")}
  serve: 8080

Fonctions utiles : param, query, body, body_json et response(status, payload). Les informations de requête existent aussi dans req. Consultez Night pour un framework web OW distinct et plus haut niveau.

Extensions runtime et SPI Java

OW dispose d'un mécanisme optionnel d'extensions runtime via des JAR Java externes. Il fonctionne avec l'interpréteur, sans garantir une compatibilité avec le backend LLVM. Un fournisseur implémente dev.oreo.RuntimeExtension et s'enregistre dans META-INF/services/dev.oreo.RuntimeExtension.

La fonction extension("provider.operation", ...) appelle le fournisseur compatible. Si aucun fournisseur ou plusieurs fournisseurs correspondent, une erreur survient plutôt qu'une sélection arbitraire. Les hooks beforeRequest et afterRequest peuvent également inspecter ou refuser des requêtes HTTP.

# Shell avec le JAR runtime OW et la plateforme Night facultative :
java -cp 'OwIDE.jar:night-platform.jar' dev.oreo.Main run app.ow

# app.ow
main:
  call: extension("night.security.enable")
  route "GET /":
    respond: "protected"
  serve: 8080
Le séparateur du classpath montré convient à macOS/Linux ; Windows utilise un point-virgule. Le fournisseur et sa configuration doivent exister pour que l'opération fonctionne. Ajouter un JAR Java ne rend pas toutes ses API directement accessibles en syntaxe OW.

Le serveur HTTP OW intégré possède actuellement un seul worker et une limite documentée à 1 Mio pour le corps des requêtes. Une exposition sur Internet nécessite notamment proxy inverse, TLS, délais et limites de requêtes. Le SPI seul n'est pas un système d'authentification.

Déployer les services web OW avec prudence

Le serveur route / serve convient aux prototypes et aux API locales. Une mise en production publique est un chantier distinct : un gestionnaire HTTP OW ne fournit pas automatiquement TLS, authentification, sessions ou protections de production.

Exemple de route et réponse

main:
  route "GET /health":
    respond: {ok: true}

  route "POST /echo":
    set data: body_json()
    respond: response(201, data)

  serve: 8080

Avant toute exposition publique

  • Installer un proxy inverse renforcé : HTTPS, protection contre les clients lents, limites de requêtes et de connexions.
  • Conserver les secrets dans la configuration/environnement, authentifier et autoriser les routes sensibles avant la logique métier.
  • Tenir compte du serveur à un seul worker et de la limite actuelle de 1 Mio par corps de requête ; valider les entrées et limiter le travail.
  • Surveiller les erreurs et effectuer des tests de déploiement réalistes. Une suite de tests verte ne remplace pas un audit de sécurité.

Pour JDBC, migrations, sécurité bearer/JWT, métriques et outbox, voir la plateforme Night facultative. Sa version candidate 0.2 n'est pas certifiée pour la production.

Interfaces web et fenêtres natives

OW peut afficher le même arbre de composants dans un navigateur (ui_run ou ui_run_web) et dans une fenêtre de bureau (ui_run_native). Les boutons et champs de saisie appellent des fonctions OW.

fn view():
  return: ui_col([
    ui_heading("Counter"),
    ui_text("Count " + str(count)),
    ui_button("+1", "increment")
  ])
fn increment():
  set count: count + 1
main:
  set count int: 0
  call: ui_run("view", "OW Counter")

Composants : ui_heading, ui_text, ui_button, ui_input, ui_image, ui_bar, ui_space, ui_card, ui_backdrop, ui_row, ui_col, ui_grid et ui_disc. ui_stop arrête l'interface.

OW_UI_MODE sélectionne le moteur ; OW_UI_NO_BROWSER=1 évite l'ouverture automatique du navigateur.

Images, champs de saisie et callbacks

Les fonctions ui_image(path) et ui_input(value, handler) de l'interpréteur sont prises en charge par le rendu web et la fenêtre native. Les chemins d'images sont relatifs au répertoire de travail du processus. Un gestionnaire de saisie reçoit le texte en chaîne de caractères lorsque l'utilisateur appuie sur Entrée.

class App:
  field word
  fn new():
    set this.word: ""
  fn on_word(value):
    set this.word: value
  fn view():
    return: ui_col([
      ui_heading("Image et saisie"),
      ui_image("assets/logo.png"),
      ui_input(this.word, "app.on_word"),
      ui_text(this.word)
    ])

main:
  set app: new App()
  call: ui_run("app.view", "Démo OW")

Les callbacks d'instance utilisent le nom d'une méthode d'objet global, par exemple app.on_word. Convertissez une valeur numérique avec int(value). Le rendu web se met à jour après l'envoi ; la saisie garde le focus tant que l'utilisateur écrit. La fenêtre native emploie un champ de texte du bureau.

Les ressources embarquées dépendent du répertoire de travail et des règles de packaging. Placez les images dans assets/ et testez les chemins avec ow run puis l'application distribuée. La prise en charge des formats varie selon le moteur de rendu.

Présentation de la compilation native LLVM

ow llvm génère du LLVM IR et ow build produit un exécutable autonome pour les constructions compatibles, sans JVM nécessaire à l'exécution. Le compilateur continue de dépendre de Java. Le sous-ensemble natif reste expérimental et incomplet.

ow llvm examples/native_dynamic_strings.ow target/strings.ll
clang target/strings.ll -o target/strings
./target/strings

Le support actuel couvre notamment les opérations entières, les fonctions typées, les chaînes UTF-8, les tableaux d'entiers/chaînes avec comptage de références, des dictionnaires spécialisés, des dictionnaires imbriqués, l'itération ordonnée et certains appels statiques à des modules/foncteurs entiers.

Les classes générales, flottants, OWUnit, try/catch, modèles de données, serveurs HTTP et interfaces graphiques ne disposent pas encore d'un support natif complet.

Chaînes, tableaux natifs et gestion mémoire

Les chaînes natives utilisent UTF-8 et prennent en charge la concaténation string + string, les comparaisons de contenu et len(string) avec la sémantique Java UTF-16. Les chaînes contenant un octet NUL intégré ne sont pas prises en charge.

fn make(size: int):
  returns: string_array
  return: array(size, "Hello " + "OW")

main:
  set names: make(3)
  print: names[0]
  print: len(names)

Les types array (entiers i32) et string_array gèrent les indices, mutations, allocations dynamiques, paramètres/retours typés et le comptage de références ARC. Les tableaux de chaînes libèrent aussi les chaînes contenues lorsqu'ils n'ont plus de propriétaire. [] crée un tableau entier vide ; pour un tableau natif de chaînes vide, utilisez array(0, "").

Les compteurs ne sont pas atomiques, l'ABI reste instable et les erreurs d'indices peuvent arrêter l'exécutable natif.

Dictionnaires natifs et parcours ordonné

LLVM dispose de maps à clés chaînes : int_map, string_map et mixed_map (valeurs typées entiers, chaînes ou maps imbriquées). Une table de hachage UTF-8 redimensionnable offre une recherche moyenne en O(1).

main:
  set cfg: {name: "OW", version: 6}
  set keys: map_keys(cfg)
  set values: map_values(cfg)
  print: keys[0]
  print: cfg["name"]

map_keys et map_values renvoient des instantanés propriétaires dans l'ordre d'insertion. Modifier une clé ne change pas sa position ; la supprimer puis la recréer la déplace à la fin. Les valeurs d'une mixed_map sont regroupées dans un mixed_array.

Les maps imbriquées utilisent ARC avec prévention des cycles. Le natif n'accepte pas encore les objets arbitraires, flottants, valeurs nulles, tableaux en valeur de map ni toutes les opérations JSON.

Détails des ABI et collections natives

Une sortie LLVM native s'exécute sans JVM, mais ne compile qu'un sous-ensemble typé. Certaines représentations ont des règles d'appartenance explicites et continuent d'évoluer. Un programme accepté par ow check ou ow run peut être refusé par ow llvm.

ReprésentationComportement expérimentalLimite principale
array (i32)Littéraux, création, accès/modification par indice, len, fonctions typées, références comptées.Pas de tableaux génériques d'objets ou de structures mixtes imbriquées.
string_arrayChaînes UTF-8 dynamiques, alias, références possédées.Pas d'objets génériques ; les règles des chaînes natives sont spécifiques.
int_map, string_mapLecture/écriture/suppression par clé texte, table de hachage extensible et parcours ordonné.Valeurs homogènes et types explicites à certaines frontières.
mixed_mapValeurs étiquetées entier/texte/dictionnaire imbriqué, accès dynamique et gestion des références.Pas d'objet, flottant, tableau comme valeur ni JSON natif général.
mixed_arrayInstantanés possédés issus de map_values, lecture indexée et fonctions typées.Pas un tableau hétérogène universel avec tous les littéraux.

Instantanés et ordre d'insertion

main:
  set settings: {language: "OW", major: 1}
  set names: map_keys(settings)
  set values: map_values(settings)
  print: names[0]
  print: values[1]

map_keys et map_values créent des instantanés. Modifier une clé conserve sa position ; supprimer puis réinsérer la déplace à la fin. Les dictionnaires imbriqués protègent contre les cycles. Une table de hachage UTF-8 extensible assure une recherche moyenne en O(1), avec un pire cas en O(n).

Les compteurs de références natifs ne sont pas atomiques. Il n'y a pas de ramasse-miettes général ni de déroulement des exceptions pour les graphes d'objets arbitraires. Les modifications d'ABI peuvent nécessiter de recompiler les anciens exécutables. Les tests AddressSanitizer/LeakSanitizer des exemples ne valent pas certification de production.

Modules et foncteurs en natif

Le backend LLVM peut compiler certains appels statiquement résolus à des modules ou foncteurs entiers, notamment des variantes qualifiées, opaques ou empaquetées documentées. Il ne constitue pas un compilateur de modules OCaml complet.

ow check examples/module_calculus/native_llvm.ow
ow llvm examples/module_calculus/native_llvm.ow target/native-modules.ll

Un fichier validé par ow check n'est pas forcément compilable avec ow llvm. Les modules dynamiques de première classe et les foncteurs arbitraires restent principalement interprétés.

OWler IDE : projets, dépendances et tests

OWler IDE est un projet distinct réalisé avec Tauri 2, Rust, React et Monaco. Il intègre les commandes OW, les dépendances et la découverte des tests. Il ne faut pas le confondre avec OwIDE, l'éditeur Java fourni dans ow-lang.

Flux de travail

  1. Créer ou ouvrir un projet OW ; les nouveaux projets incluent un exemple source, dependencies.yml et un test OWUnit.
  2. Utiliser les actions pour ow check, ow run, ow llvm ou ow build. L'IR LLVM est sauvegardé dans build/owler/.
  3. Cliquer droit sur le dependencies.yml racine puis sélectionner Reload Dependencies : mise à jour du résolveur, du lockfile et des fichiers du projet.
  4. Lancer un test avec l'icône verte à côté de @Test ou exécuter tous les tests depuis la fenêtre Tests.
  5. Utiliser Reload Project après des modifications externes via un CLI d'IA ; les modifications non enregistrées ne doivent pas être effacées silencieusement.
# Commandes réellement déléguées à OW
ow deps update
ow check src/main.ow
ow test tests/
ow test tests/CalculatorTest.ow --filter CalculatorTest.additionWorks
ow llvm src/main.ow build/owler/main.ll
Le dépôt OWler décrit un IDE enrichi et des pipelines d'installateurs, sans affirmer disposer actuellement d'un installateur Windows certifié pour la production. Consultez les builds et la checklist de publication. OWUnit fonctionne via l'interpréteur et non via LLVM.

Résolution des problèmes

  • ow introuvable : ajoutez le répertoire bin/ au PATH, ou exécutez le JAR.
  • Version Java incompatible : utilisez Java 17+ ou un installateur avec runtime inclus.
  • Compilateur natif absent : installez LLVM/Clang ou Zig ; ow run n'en a pas besoin.
  • Type non pris en charge par LLVM : testez avec l'interpréteur et consultez la documentation précise du type natif.
  • Import @alias introuvable : lancez ow deps install et vérifiez le manifeste/lockfile.
  • Test non découvert : nommez le fichier avec le suffixe Test.ow ou _test.ow.
  • Erreur de frontière d'import : utilisez api/ plutôt que l'infra/ privée d'un autre module.
  • Modèle vocal absent : téléchargez un modèle Vosk et fournissez son dossier.

Pour signaler un bug, joignez un petit programme reproduisant l'erreur et précisez si le problème apparaît avec ow run, ow check ou ow llvm.

flOW : framework d'applications modulaires

flOW est un framework distinct qui relie les signatures/foncteurs natifs d'OW à un runtime inspiré de Spring Modulith pour les services, dépendances, événements et cycles de vie. Il n'ajoute pas de nouvelle syntaxe au compilateur.

Passerelle des modules natifs

set orders ORDERS: MakeOrders(Warehouse)
set app: new App()
call: app.use_native_as(orders, "ORDERS")
call: app.use_native_as(Warehouse, "INVENTORY")
call: assert(app.boot() == 1)
set inventory INVENTORY: app.service("inventory")
call: app.emit("order.placed", 5)
call: app.stop()

use_native et use_native_as enregistrent des modules réellement typés via un adaptateur de runtime, en préservant le contrat lors de leur récupération. use conserve la compatibilité avec les anciens modules à base de classes. Les événements natifs utilisent actuellement des charges utiles entières et des noms de type chaîne.

Règles du cycle de vie

  • boot() démarre les fournisseurs dans l'ordre des dépendances ; stop() les arrête dans l'ordre inverse.
  • disable(name) refuse l'arrêt d'une dépendance nécessaire à des modules actifs ; enable(name) n'active un module que si ses dépendances tournent.
  • reload(name) s'applique aux modules actifs. emit notifie uniquement les modules démarrés et activés.
  • Un résultat start négatif interrompt le démarrage et annule les démarrages déjà réussis.
Limites courantes : 64 modules, 128 exigences typées et 64 services par registre ; après un démarrage en échec, recréer App. La passerelle est gérée par l'interpréteur : LLVM ne compile pas généralement les valeurs d'adaptateur de cycle de vie.

Night : framework web et modules starters

Night sert à créer des applications web modulaires avec le runtime OW, les contrats de modules natifs et une plateforme Java ServiceLoader facultative. Il s'inspire de Spring Boot et Spring Modulith, sans être Spring Boot ni permettre d'importer automatiquement toutes les bibliothèques Java depuis OW.

Night 0.2 est une fondation testée pour l'intégration, pas un remplaçant certifié de Spring Boot. OIDC/OAuth2 complet, ORM, Kafka/Streams, WebSockets, GraphQL, serveur non bloquant et audits de production restent à développer. LLVM ne sait pas embarquer un runtime Night général.
